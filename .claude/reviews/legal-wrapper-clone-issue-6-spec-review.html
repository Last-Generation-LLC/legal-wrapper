Three departures from the handoff:
· the serif title is a static "Workspace" label, not a matter name 4
· the meter fills but does not warn yet 5

The ~ prefix marks an estimated token count. The inline red strip surfaces upload errors 8; the bare panel is the zero-document state 9.

The schema gap, and what each row can honestly show

The handoff row reads MSA · 42p · 31.4k tok and its header carries 284 KB. None of that survives contact with our data. The Document model (prisma/schema.prisma) stores only filename, an optional title, mimeType, the extracted text, a tokenCount, and a tokenCountEstimated flag. There is no document-type taxonomy (MSA/DPA/NDA), no page count, and no byte size. Inventing those fields in the UI would be exactly the confident-but-fabricated display this product exists to argue against. So each row shows what we genuinely know: a format badge derived from mimeType (PDF or DOCX), the token count, a ~ prefix when that count is estimated, and title ?? filename as the label 3.

Where the panel lives, and how the list loads

Two structural questions sit underneath the pixels. First, where the sidebar mounts. The Review screen (design_handoff_legal_wrapper/components/review.jsx) is its own grid layout with its own document set — the sidebar is not a global workspace element, it belongs to the Assistant. So rather than push it into the shared shell (src/app/(workspace)/layout.tsx), the plan adds an Assistant-scoped layout that wraps a DocSidebar client component and the chat page in a single DocsProvider React context. That provider holds documents, selectedDocs, and a toggle function; the future chat (#9) reads the same selection through a useDocs() hook instead of re-deriving it 1.

Second, how the existing document list arrives. There is no GET /api/documents endpoint. The plan does not add one: an Assistant Server Component calls prisma.document.findMany (selecting metadata only, never the extracted text) and seeds the provider; after a successful upload the client calls router.refresh() to re-run that server fetch and repaint the list. This reuses the existing @/lib/prisma singleton, adds no new route to test or secure, and fits the App Router grain 2. The live meter, selection, and what stays out of scope

Clicking any row toggles its checkbox and updates two things at once: the In Context · {count} label and the amber meter. The meter math is selectedTokens / 180000, clamped to 100%, drawn as a 3px amber bar, labelled {k}k / 180k — a direct port of the handoff. What it deliberately does not do is warn or block near the ceiling; the token-guardrail behavior (the warning band, the hard error at the limit) is task #16 and stays out of this build 5. The selection itself is in-memory React state only — it resets on reload, with no database or localStorage persistence, matching MVP simplicity 6.

The serif header line, which in the handoff reads Aperture · MSA Renewal, has no backing entity in our MVP — there is no "matter" or "workspace" record. It becomes a static product label ("Workspace"), and the mono sub-line below it is computed live as {N} documents · {total} tokens across all uploaded docs, not just the selected ones 4.

Failure paths worth getting right now

The upload route already returns structured errors — 400 for an unsupported or empty file, 413 past the 25 MB cap, 422 when extraction fails (a scanned PDF, say). The sidebar must surface these, not swallow them. The full toast system is task #17, so the mitigation here is the minimal inline red strip shown in the mockup, sitting just under the header until the next action 8. Separately, a fresh clone has an empty database; the list, meter, and counts all have to render sensibly at zero. Polished empty states are also #17, so the mitigation is the simple "No documents yet" placeholder shown above 9.

Reuse, not reinvention

Everything visual here is assembled from primitives that already exist (#4). The Upload control is the existing <Btn variant="ghost" size="sm" icon="upload">; the checkmark is <Icon name="check" size={9} strokeWidth={3} />; format and empty-state glyphs come from the semantic icons map (doc, folder, upload). The dark tokens (bg-bg, bg-panel-hi, border-soft, text-amber, text-dim, font-serif, font-mono) are consumed as Tailwind utilities — no new colors, no shell restyling. The one bespoke piece is the 14px amber checkbox, which the handoff itself builds inline rather than as a shared component, so it is built inline here too — not promoted to a new primitive. Tests follow the established pattern: Vitest in node by default, this component opting into jsdom per-file and asserting against @testing-library/react 10.

Should the sidebar and its selectedDocs state be Assistant-scoped, or live in the global workspace layout?

The Review screen has its own grid layout and its own document set, so the 280px sidebar is not a global element — pushing it into (workspace)/layout.tsx would force it onto Review and Documents where it does not belong.

Recommendation (A): add an (workspace)/assistant/layout.tsx that mounts a DocSidebar client component beside the page inside a DocsProvider context (documents, selectedDocs, toggle). The future chat (#9/#10) reads selection via a useDocs() hook. Tradeoff: one more layout file and a context provider, versus a cleaner boundary and no leakage of Assistant-only state into other routes.

There is no GET /api/documents endpoint — how should the sidebar load the documents already in the database?

Recommendation (A): an Assistant Server Component calls prisma.document.findMany (metadata-only select, never the extracted text), seeds the DocsProvider, and the client calls router.refresh() after a successful upload to repaint. Reuses the existing @/lib/prisma singleton, adds no new route to build/secure/test, and fits the App Router grain.

Tradeoff: the list only refreshes on a server round-trip (fine here — uploads are the only mutation). Option B (a client-fetched JSON route) is more familiar and decouples the list from server rendering, but it is a new endpoint to maintain for no current benefit.

What should each row's metadata line show, given we store no document type, no page count, and no byte size?

The handoff's MSA · 42p · 31.4k tok is fictional for our data. Displaying invented fields is the exact failure mode this product critiques.

Recommendation (A): {FORMAT} · {tokens}k tok where FORMAT is PDF/DOCX from mimeType, a ~ prefix when tokenCountEstimated is true, and the row label is title ?? filename. Drop the page count and the MSA/DPA taxonomy.

Tradeoff: rows carry less at-a-glance metadata than the mock implies. This is a product display choice — not deferrable — but it has a clear recommendation.
