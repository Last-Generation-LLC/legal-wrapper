# Persist chat history to SQLite (save/restore Assistant thread)

## Description
Triaged from GitHub issue #22 on 2026-06-12. See the issue for full detail.

## Acceptance Criteria
- [x] Issue #22 resolved and closed

## Decisions

- User decision (2026-06-12): Option "A now, B as follow-up" — ONE auto-saved
  thread, reload-safe; "New session" ARCHIVES the old thread (archivedAt) and
  starts fresh; session-list browsing UI filed as issue #26.
- Active session = the single ChatSession with archivedAt = null, created
  lazily on first use.
- Each Message row stores the FULL AI SDK UIMessage as JSON in `content`
  (text parts + data-citations + metadata), so citations, confidence, and
  token usage round-trip exactly. Row id = the UIMessage id; `role` kept as a
  queryable column. Malformed rows are skipped on load, never crash.
- Write path (server, in the chat route): replace-all of the incoming
  messages array BEFORE streaming (the client's array is the truth — this
  inherits edit/truncate/regenerate semantics for free), then append the
  final assistant message AFTER the stream finishes. A mid-stream reload
  loses only the unfinished assistant text.
- Read path: server components load the active thread; useChat starts from
  the stored messages. Doc selection persists per session
  (ChatSession.selectedDocIds, JSON array; stale ids silently dropped) and
  restores with the thread.
- Schema migration: ChatSession += archivedAt DateTime?, selectedDocIds
  String @default("[]").
- "New session" keeps the current doc selection (it's a working set, not a
  message); the new session records its own selection on first send.
